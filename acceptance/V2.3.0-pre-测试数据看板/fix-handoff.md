## B1-残留 · 顶部「关键指标环比概览」的递交小卡仍透传 BUG 归属筛选

**严重度**：轻微（主区块已按"BUG 筛选只影响 BUG、递交只受统计周期影响"的设计工作，仅顶部环比卡不一致）

### 现象（2026-07-27 实测）
选「BUG归属部门=项目开发」（dept_id=7）后：
- 「递交维度分析」区块保持全量 65 ✔（已修复，符合设计）；

### 顺带口径确认（请开发/产品明确）
无筛选时「准时递交率」当前为 93.85%（按时 61/65，tooltip「点击查看未准时递交（超时）明细」，疑似=总数−超时），但下方「递交数据概览」的「按时递交」显示 63（正常+提前）。同屏两种"按时"口径并存，建议统一或在 UI 标注差异。

### 通过标准
```
UI：选「BUG归属部门=项目开发」后，「关键指标环比概览-递交数据环比」各卡
    应显示全量数据（准时递交率非 0/0），与「递交维度分析」区块一致。
UI：选「BUG归属人」同上。
口径：PM 筛选对 KPI 递交环比是否生效、「准时递交率」分子口径（63 还是 61），
    明确后在页面副标题注明，两个区块保持同一响应逻辑。
```

## B3 · 补录递交（无计划时间）在「递交列表」模块任何日期范围都查不到

**严重度**：轻微（看板统计本身正确，但列表侧核对必差 5 条）

### 现象与数据锚点
看板 2026-07 全部递交 65 条中 5 条 `plan_publish_time` 为空：
#14260（厦门-同安区，超时）/ #14269（玉禾田，超时）/ #14290（亿滋工厂，超时）/ #14308（玉禾田，超时）/ #14286（阿布扎比 Data Center，延期）。
「递交列表」`project_publish/get_list?begin=&end=` 按**计划时间**过滤，这 5 条计划时间为空 → 2025、2026 全年范围都拉不到（实测 diff：看板 65 = 列表 60 + 这 5 条,「列表有看板无」=0）。

### 定位线索
- 这批是超时/延期的补录递交（real_publish_time 有值、plan 为空）。
- get_list 的 begin/end 直接作用于 plan 字段，空值被排除。

### 通过标准
```
project_publish/get_list 支持按实际递交时间筛选（或空计划时间兜底展示）后：
  按 real_publish_time ∈ 2026-07 查询应返回 65 条，包含上述 5 个 id。
```

## B4 · 看板下钻明细/延期清单 时间列显示 `2006-01-02 15:04:05`（Go 零值模板）

**严重度**：中（不影响统计数字，但明细时间列全部错值，用户可见误导）

### 现象
- 下钻明细弹窗（`get_qa_stat_detail_list`，如 chart_key=bug_status&option_id=resolved）返回的 `submit_time` **全部**为 `2006-01-02 15:04:05`；
- 延期清单（`get_qa_stat_publish` 的 `delay_list[].real_publish_time`）同样返回 `2006-01-02 15:04:05`。

### 数据锚点（对照源头，实锤是展示接口的错，不是脏数据）
| 记录 | 源头 bug/get_list | 看板 detail_list |
| --- | --- | --- |
| BUG #546 | submit_time = 2026-07-03 00:00:00 ✔ | 2006-01-02 15:04:05 ✗ |
| BUG #547~#551 | 2026-07-10/17 等正常 | 全部 2006-01-02 15:04:05 ✗ |

### 定位线索
`2006-01-02 15:04:05` 是 Go 时间格式化 layout 常量（`2006-01-02 15:04:05` 即 Go 的参考时间）。后端疑似把 layout 字符串当作**值**输出，如 `time.Format` 误写成常量、或对空 time.Time 格式化。请检查 `get_qa_stat_detail_list` / `get_qa_stat_publish` 组装响应处的时间格式化代码。

### 通过标准
```
get_qa_stat_detail_list(chart_key=bug_status, option_id=resolved, 2026-07)
  返回的每条 submit_time 应等于 bug/get_list 同 id 记录的 submit_time（如 #546=2026-07-03）；
get_qa_stat_publish(2026-07).delay_list[].real_publish_time 不得出现 2006-01-02。
```
